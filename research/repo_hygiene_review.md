# Repository hygiene review

Date: 2026-09-26

## Scope

This is a pre-commit, read-only review of the repository contents,
apart from writing this report. It covers file inventory, file sizes,
likely secrets, generated content, acquired or vendored content, and
the proposed Git boundary.

No commit exists at `HEAD`. The repository was initialized while this
review was in progress. No files were staged when the final inventory
was inspected.

## Executive result

Do not make the initial commit yet.

The current `.gitignore` is effective at excluding nearly all bulky,
generated, machine-local, and plainly secret-bearing artifacts. It
reduces the prospective tracked set from approximately 285 MiB across
3,156 files to approximately 1.16 MiB across 99 files.

There is one confirmed secret disclosure in the unignored set:

- `research/post_provision_commit_diff.md` contains the exact live
  application key stored in `mesh-lab/sphere_state.json`.

There is also a second high-risk document:

- `research/self_provision_plan.md` contains literal 128-bit values
  explicitly labeled as a network key and application key. They do
  not match the current state file, but they could be previous or
  still-valid credentials. They should not be committed unless they
  are conclusively identified as public test vectors or replaced with
  unmistakable non-secret placeholders.

No secret values are reproduced in this report.

## Resolution before initial commit

The confirmed live AppKey and the ambiguous experimental NetKey and
AppKey were replaced with semantic redaction markers. A second exact
comparison against every current live mesh key found zero matches in
the staged tree.

After dependency review, the upstream mesh library was not committed
as a vendor snapshot. `requirements.txt` now pins upstream version
0.10.3 by its full Git commit because PyPI exposes only 0.1.0. Two
local differences found in the former working copy were isolated into
the first-party `sphere_transport.py` and `sphere_access.py` modules
and covered by project tests. The local `vendor/` cache remains
ignored.

## Secret and privacy findings

### Confirmed live-key disclosure

An equality check against all six sensitive fields in the current
mesh state found the live application key in
`research/post_provision_commit_diff.md`. Redact it before staging.
Use a semantic placeholder such as `<redacted-app-key>` rather than a
different plausible-looking 128-bit value.

The ignored provisioned-state backup contains the current network key,
application key, and one current device key. Its ignore coverage is
correct, but it should be handled as a credential backup, not merely
as build output.

### Other literal mesh keys

`research/self_provision_plan.md` contains literal values labeled
`NetKey` and `AppKey`, including command examples. Their mismatch with
the current state does not prove they are safe. Redact them, replace
them with a documented public test vector, or rotate the corresponding
network before committing them.

Several tests and the vendored test fixture contain 128-bit values.
These appear in test-vector contexts and are not exact matches for the
current live keys. Keep them only when their public or synthetic origin
is clear.

### Local state, captures, and logs

The following artifacts are correctly ignored and should remain so:

- `mesh-lab/sphere_state*.json`, which contains network, application,
  and device keys plus sequence and address state;
- `mesh-lab/*.log`, which records device addresses and protocol data;
- all `*.btsnoop`, `*.pcap`, and `*.pcapng` captures;
- `proxy_pdus.csv`, a decoded capture-derived export; and
- `phone_external/`, including device/app logs and cached mini-app
  content.

Git exclusion is not an operating-system confidentiality control. The
two state files are mode `0600`, which is appropriate. The captures and
log inspected were mode `0644`, and `phone_external/` was traversable
by other local users. If the host is multi-user, restrict those local
permissions and protect any off-repository backup.

### Secret-scan limitations

The scan found no PEM-style private-key header in the text corpus.
Keyword and fixed-width token scans are necessarily heuristic. They
cannot prove that compressed APK content, captures, minified app code,
or arbitrary blobs are safe. Those entire classes should stay outside
Git rather than relying on content scanning.

## Generated and acquired content

The current ignore rules correctly cover:

- `.venv/`, Python bytecode, pytest caches, and common tool caches;
- APK, XAPK, and Debian package files;
- Bluetooth captures, logs, and decoded CSV output;
- the phone export;
- extracted tools; and
- mesh runtime state and daemon/client state directories.

The root and vendored `__pycache__` trees and vendored pytest caches are
therefore absent from the prospective commit.

The blanket `tools/` ignore is accurate for the current contents, all
of which are extracted distribution payloads. A narrower
`tools/bluez-meshd-root/` rule would be safer if project-authored helper
scripts may later be added beneath `tools/`; otherwise Git can silently
hide those new sources.

Similarly, `.env.*` also ignores a future `.env.example`. Add a
specific exception if a sanitized environment template is introduced.

## Vendored content

`vendor/ha-bluetooth-mesh/` is suitable to track as an intentional
vendor snapshot after generated caches are excluded:

- `PROVENANCE.md` names the upstream URL, exact commit, version,
  retrieval date, included paths, and MIT license;
- `LICENSE` is present;
- source, tests, package metadata, and the lock file are included; and
- generated bytecode and pytest caches are ignored.

Keep the provenance file adjacent to the vendored code. When updating
the snapshot, update its upstream commit and retrieval date in the
same change. Avoid mixing local modifications into a future upstream
refresh without documenting them as patches or a maintained fork.

The Olight APK and phone mini-app files are a different category. They
are third-party acquired content with redistribution and privacy risk,
not source dependencies. Keep them outside repository history. Record
only non-sensitive provenance, version, hashes, acquisition method,
and any relevant license status in research documentation.

The Debian packages and their extracted BlueZ/ELL binaries are also
replaceable, platform-specific downloads. Prefer documented package
names and versions over committing either the packages or extracted
payloads.

## Recommended tracked organization

Track these categories:

- root `.gitignore` and `README.md`;
- first-party Python sources, launcher, and tests;
- project documentation and research notes after key redaction;
- `mesh-lab/mesh-main.conf` if it is a generic, portable baseline;
- the vendored library's source, tests, metadata, lock file, license,
  and provenance record; and
- this hygiene report, after the confirmed disclosure is resolved.

Keep these categories ignored and backed up separately where needed:

- live mesh state and all state backups;
- captures, logs, and decoded protocol exports;
- phone exports and application caches;
- APKs, Debian packages, and extracted system binaries;
- virtual environments and all generated caches; and
- app-local agent metadata.

Consider moving durable raw evidence to a sibling directory outside
the Git worktree. A small tracked artifact manifest can preserve its
filename, source, version, hash, and sensitivity classification without
making the binary or credential-bearing content easy to stage.

## Reproducibility and documentation gaps

There is no root dependency manifest. The first-party tools import
third-party packages including `cryptography`, `bleak`, and the
vendored `btmesh` package, while the README currently assumes an
already-created `.venv`. Add a root `pyproject.toml`, requirements
file, or an explicit setup section so the ignored environment can be
recreated.

Several research notes link to ignored local artifacts. That is useful
for the original workstation but produces unavailable links in a
clone. Mark these as local-only evidence and, where useful, cite a
tracked manifest entry instead.

`PROMPT.md` appears to be project context rather than implementation.
Track it only if preserving the original task specification is an
intentional repository goal.

## Pre-commit gate

Before the initial commit:

1. Redact the exact live application key from
   `research/post_provision_commit_diff.md`.
2. Resolve every literal key in `research/self_provision_plan.md` by
   redaction, proof of public test-vector origin, or credential
   rotation.
3. Re-run an exact-value scan from the live state against every staged
   blob without printing the values.
4. Review `git status --ignored` and verify no ignored artifact was
   force-added.
5. Inspect the staged file list and largest staged blobs.
6. Run a general secret scanner over the staged tree and manually
   review findings in research notes and fixtures.
7. Run tests and `git diff --cached --check`.
8. Confirm that vendored provenance, license, and lock data are staged
   with the vendored source.

The initial commit is hygiene-ready only after the confirmed key leak
and the ambiguous literal mesh keys are resolved.
